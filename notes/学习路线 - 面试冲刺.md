## 一、说明

适合两三周内就要面试、已经学过这些内容的读者，每天 1.5～2 小时，覆盖约 40 个核心考点，最后 1 天是大模型应用。应聘大模型应用岗位的读者，用[大模型应用开发](学习路线%20-%20大模型应用开发.md)每天的自测题复习。

2. ConcurrentHashMap 怎样保证线程安全？JDK 1.7 和 1.8 有什么区别？（见[JDK 1.8 的改动](Java%20容器.md#3-jdk-18-的改动)）
3. ArrayList 和 LinkedList 有什么区别？（见[与 ArrayList 的比较](Java%20容器.md#2-与-arraylist-的比较)）

<details>
<summary>参考要点</summary>

1. JDK 1.8：table 为空先 resize()，用 (n - 1) & hash 定位桶，空桶直接放入；否则头节点是 TreeNode 就在红黑树中查找或插入，是链表就逐个比较，键相同就替换旧值，找不到就接在链表尾部；插入后 size 大于 threshold（容量 × 0.75，默认 12）时扩容为 2 倍；接上前链表已有 8 个节点时，数组长度小于 64 只扩容，否则转成红黑树。
2. JDK 1.7 用分段锁，Segment 继承 ReentrantLock，默认 16 个，并发度创建后不能改变；JDK 1.8 去掉 Segment，空桶用 CAS 放入，非空时 synchronized 锁住桶的头节点，锁粒度到桶，多个线程可以一起迁移扩容；get 不加锁，靠 volatile 读到最新值。
3. ArrayList 基于动态数组，随机访问快，中间插入删除要移动元素，但一次复制一整块连续内存；LinkedList 基于双向链表，插入删除只改指针，但要先 O(N) 遍历到位置；实测 10 万个元素中间插入 1 万次，ArrayList 约 50 ms、LinkedList 约 0.8～1 秒，多数场景用 ArrayList。

</details>

必学：[ThreadPoolExecutor](Java%20并发.md#threadpoolexecutor)、[synchronized 与 ReentrantLock 的比较](Java%20并发.md#比较)、[内存模型三大特性](Java%20并发.md#内存模型三大特性)、[volatile](Java%20并发.md#volatile)。

自测：

2. synchronized 和 ReentrantLock 有什么区别？（见[synchronized 与 ReentrantLock 的比较](Java%20并发.md#比较)）
3. volatile 能保证什么，不能保证什么？（见[volatile](Java%20并发.md#volatile)）

<details>
<summary>参考要点</summary>

1. 参数有核心线程数、最大线程数、空闲线程的存活时间、任务队列、线程工厂和拒绝策略；提交时线程数小于核心数就新建线程，否则放入队列，队列满且小于最大线程数时新建线程执行当前任务，再不行就执行拒绝策略；例如核心 2、最大 4、队列 2 时第 7 个任务被拒绝；不用 Executors 的 newFixedThreadPool()、newSingleThreadExecutor()、newCachedThreadPool()，它们的队列或线程数没有上限，要直接创建 ThreadPoolExecutor 并使用有界队列。
2. synchronized 由 JVM 实现（代码块编译为 monitorenter、monitorexit，方法用 ACC_SYNCHRONIZED 标志，异常时也会释放锁），ReentrantLock 由 JDK 基于 AQS 实现；新版本中在平台线程上两者性能大致相同，但 JDK 21 的虚拟线程在 synchronized 内阻塞会固定载体线程，这时要用 ReentrantLock；ReentrantLock 等待可中断、可以设为公平锁、能绑定多个 Condition，synchronized 都不能。
3. 保证可见性：写入后其它线程读取时立即可见；保证有序性：volatile 写之前、volatile 读之后的读写不会被重排序越过它，可用来发布数据（如双重校验锁单例）；不保证 count++ 这类复合操作的原子性，要用锁或原子类。

</details>

### 第 3 天：CAS、锁升级与 ThreadLocal

必学：[非阻塞同步](Java%20并发.md#非阻塞同步)、[锁升级的过程](Java%20并发.md#锁升级的过程)、[线程本地存储（Thread Local Storage）](Java%20并发.md#2-线程本地存储thread-local-storage)。

自测：

1. CAS 的原理是什么？ABA 问题怎么解决？（见[CAS](Java%20并发.md#1-cas)、[ABA](Java%20并发.md#3-aba)）
2. synchronized 的锁升级过程是怎样的？（见[锁升级的过程](Java%20并发.md#锁升级的过程)）
3. ThreadLocal 为什么可能导致内存泄漏？（见[线程本地存储（Thread Local Storage）](Java%20并发.md#2-线程本地存储thread-local-storage)）

<details>
<summary>参考要点</summary>

1. CAS 有内存地址 V、预期旧值 A、新值 B 三个操作数，只有 V 等于 A 时才写入 B，由处理器指令保证原子性（x86 上是带 lock 前缀的 cmpxchg）；ABA 指值从 A 变成 B 又变回 A，CAS 误以为没变，对无锁栈这类结构有害；用 AtomicStampedReference 给引用加版本号，每次修改加 1。
2. 无锁（Mark Word 末尾 01）；轻量级锁（00）：线程用 CAS 把 Mark Word 换成指向栈中 Lock Record 的指针，重入只多放一个 Lock Record；重量级锁（10）：其它线程 CAS 失败时膨胀为 ObjectMonitor，先自适应自旋，仍抢不到再阻塞；JDK 15 起默认禁用偏向锁，空闲的 ObjectMonitor 会被回收，对象恢复为无锁。
3. ThreadLocalMap 的 Entry 对 key（ThreadLocal）是弱引用、对 value 是强引用；ThreadLocal 没有其它强引用时 key 被回收变为 null，value 仍被线程的 Map 引用，之后这个线程调用 set()、remove() 或没有直接命中的 get() 时可能顺带清理，线程池中的线程一直存活又没有触发清理时，value 就一直留着；用完在 finally 中调用 remove()，也能避免线程复用时读到上一个请求的值。

</details>

自测：

<details>
<summary>参考要点</summary>

1. 线程私有：程序计数器、Java 虚拟机栈（每个方法一个栈帧，-Xss 设置大小）、本地方法栈；线程共享：堆（几乎所有对象，分新生代和老年代，-Xms、-Xmx 设置）和方法区（类的元信息和运行时常量池，JDK 8 起由本地内存中的元空间实现；字符串常量池和静态变量 JDK 7 起已移到堆中，JIT 编译的代码在单独的代码缓存中）；NIO 还会使用堆外的直接内存；除程序计数器外都可能 OOM，两种栈还可能 StackOverflowError。
2. 范围：CMS 只回收老年代，要配合 ParNew，G1 把堆分成等大的 Region，混合回收时新生代和老年代一起回收；碎片：CMS 用标记 - 清除，碎片多时只能 Full GC 整理，G1 把存活对象复制到空闲 Region，普通对象不产生碎片（Humongous 对象要连续 Region，仍可能因找不到连续空间提前触发 GC）；停顿：G1 按停顿目标（默认 200 ms）优先回收价值最大的 Region，更可预测，代价是额外内存，吞吐量通常略低于 Parallel；JDK 9 起服务器级机器默认使用 G1，JDK 14 移除了 CMS。
3. 先看错误信息判断是哪块内存不足（Java heap space、Metaspace、direct buffer memory、unable to create native thread），Metaspace 查动态生成的类和不能卸载的类加载器，unable to create native thread 查线程数和系统限制，增大堆没有用；Java heap space 时用 -XX:+HeapDumpOnOutOfMemoryError 自动保存堆转储或用 jcmd 导出，再用 MAT 按 Retained Heap 找占用最多的对象及其到 GC Roots 的引用链；不该存活就是泄漏（静态集合、ThreadLocal 未 remove、资源未关闭），改代码，否则增大堆或减少一次加载的数据；慢泄漏可以定期用 GC.class_histogram 比较实例数。

</details>

## 四、MySQL

### 第 5 天：索引

必学：[B+ Tree 原理](MySQL.md#b-tree-原理)、[MySQL 索引](MySQL.md#mysql-索引)、[索引优化](MySQL.md#索引优化)、[索引失效](MySQL.md#索引失效)。

自测：

1. MySQL 为什么用 B+ 树做索引？（见[B+ Tree 原理](MySQL.md#b-tree-原理)）
2. 什么是聚簇索引、回表和覆盖索引？（见[B+Tree 索引](MySQL.md#1-btree-索引)、[覆盖索引](MySQL.md#5-覆盖索引)）
3. 联合索引的最左前缀是什么？哪些情况下索引会失效？（见[多列索引](MySQL.md#2-多列索引)、[索引失效](MySQL.md#索引失效)）

<details>
<summary>参考要点</summary>

1. B+ 树的一个节点就是一个 16 KB 的页，有几百上千个子节点，树很矮（200 万行的主键索引 3 层，二叉树约 21 层），一次 I/O 读一个节点，读盘次数少；内部节点只存 key 和指针，比 B 树每页放的 key 更多，每次查找都走到叶子、I/O 次数稳定；叶子按顺序用指针相连，范围查询顺序扫描即可。
2. 聚簇索引：InnoDB 主键索引的叶子节点保存整行数据，一张表只有一个；二级索引的叶子保存索引列和主键值，查其它列时先拿到主键，再到聚簇索引查出整行，这就是回表；覆盖索引指索引中已包含查询需要的全部列（含主键），不需要回表，Extra 为 Using index。
3. 联合索引先按第一列排序、再按第二列，所以条件要从最左列开始连续使用才能定位，与 WHERE 中的书写顺序无关，范围条件之后的列一般不能再缩小扫描范围（带等号时例外）；常见的无法用索引定位的情况：缺少最左列（8.0.13 起少数情况可跳跃扫描）、对索引列用函数（可建函数索引）、字符串列与数字比较、LIKE 以 % 开头、OR 一侧没有索引；匹配的行太多时，优化器按成本选择全表扫描。

</details>

<details>
<summary>参考要点</summary>

1. 用 SET lock_key unique_value NX PX 30000 一条命令加锁并设置过期时间；释放时用 Lua 脚本比较 value 是自己的才删除，避免误删别人的锁；业务超时锁会提前释放，需要续期，Redisson 的看门狗每 10 秒把过期时间重置为 30 秒，并用哈希计数支持可重入；主从是异步复制，切换时锁可能丢失；这种情况和续期失败都会让两个客户端同时持锁，正确性要求高时用栅栏令牌或数据库的唯一约束、条件更新兜底。
2. 不丢：发送端收到确认才算成功（如 Kafka acks=all 加重试），可用与业务同事务的本地消息表；存储端持久化加多副本，消费端处理完再提交偏移量或 ack；不重复：处理完才确认意味着可能重复投递，消费要幂等，用订单号加事件类型这类业务键写去重表并与业务同事务，或用状态做条件更新；消息队列的恰好一次代替不了业务幂等。
3. 超卖源于判断库存和扣减库存不是原子操作；数据库中可用悲观锁 SELECT ... FOR UPDATE、乐观锁版本号或条件更新 UPDATE ... SET stock = stock - 1 WHERE stock > 0；实测 1000 个用户抢 100 件，先查再扣多卖了 34～62 件，悲观锁和条件更新都恰好卖出 100 件；乐观锁不会超卖，但冲突多时会少卖，150 个用户抢、重试 3 次也只卖出 48～57 件；条件更新不需要重试、最常用；秒杀时先用 Redis 的 Lua 脚本挡住大部分请求，数据库的条件更新作为最后一道防线。

</details>

<details>
<summary>参考要点</summary>

1. 离线：解析文档、切片，用 Embedding 模型转为向量存入向量数据库，同时建立关键词索引；在线：改写问题，向量和关键词两路召回，合并后重排，把最相关的几段和问题放进提示词，生成带引用的回答；每一环都影响最终效果，解析错了或资料没被召回，后面无法弥补。
2. 组成：模型决定下一步，工具、记忆、规划提供能力，控制循环执行工具并限制步数、校验参数和权限；Function Calling：请求附上工具的名称、用途和参数 JSON Schema，推理服务拼进提示词，模型需要时生成特定格式的文本，服务解析为 tool_calls 返回；应用校验后执行，以 tool 消息和 tool_call_id 发回结果，本质仍是生成文本，必须先校验。
3. Function Calling 是模型侧的能力，模型根据工具描述给出函数名和参数；MCP 是应用与外部工具、数据之间的协议，统一工具的发现（tools/list）和调用（tools/call），工具实现一次服务端就能被所有支持 MCP 的应用使用；两者配合：主机把 MCP 工具转成工具定义交给模型，再通过 MCP 执行模型给出的调用。

</details>
