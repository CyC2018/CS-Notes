## 进程与线程

### 1. 进程

进程是资源分配的基本单位。

进程控制块（Process Control Block, PCB）描述进程的基本信息和运行状态，所谓的创建进程和撤销进程，都是指对 PCB 的操作。PCB 中记录了进程 ID、状态、换下 CPU 时保存的寄存器、页表和打开的文件等。

程序是磁盘上的可执行文件，进程是程序的一次运行，同一个程序启动两次就是两个进程。

### 2. 线程

线程是独立调度的基本单位。

一个进程中可以有多个线程，它们共享进程资源。

QQ 和浏览器是两个进程，浏览器进程里面有很多线程，例如 HTTP 请求线程、事件响应线程、渲染线程等等，线程的并发执行使得在浏览器中点击一个新链接从而发起 HTTP 请求时，浏览器还可以响应用户的其它事件。

<div align="center"> <img src="pics/process-threads.png" width="740px"/> </div><br>

同一进程中的线程共享地址空间（代码、全局变量、堆）、打开的文件描述符、信号的处理方式和当前工作目录等；每个线程独有的是线程 ID、程序计数器和寄存器、栈、信号屏蔽字、errno 和线程局部存储（见 [pthreads(7)](https://man7.org/linux/man-pages/man7/pthreads.7.html)）。

需要注意的是，各线程的栈只是分开使用，并没有隔离：拿到另一个线程栈上变量的地址，同样可以读写它。

### 3. 区别 🔥🔥

- 拥有资源：进程是资源分配的基本单位，但是线程不拥有资源，线程可以访问隶属进程的资源；
- 调度：线程是独立调度的基本单位，在同一进程中，线程的切换不会引起进程切换，从一个进程中的线程切换到另一个进程中的线程时，会引起进程切换；
- 系统开销：由于创建或撤销进程时，系统都要为之分配或回收资源，如内存空间、I/O 设备等，所付出的开销远大于创建或撤销线程时的开销。类似地，两者切换时都要保存和恢复寄存器，进程切换还要切换地址空间，开销更大（见[上下文切换](#4-上下文切换)）；
- 通信方面：线程间可以通过直接读写同一进程中的数据进行通信，但是进程通信需要借助 IPC；
- 健壮性：进程之间相互隔离，一个进程崩溃不影响其它进程，而一个线程访问非法内存触发段错误时，整个进程连同其它线程都会被终止。

在 Linux 内核中，进程和线程都用 task_struct 表示，都是调度的对象，区别只在于和创建者共享了多少资源。fork 和 pthread_create 最终都调用 clone 系统调用，只是传入的标志不同（strace 实测，见[附录 A4](#a4-fork-与-pthread_create-的-clone-标志)）：

```text
fork()            clone(flags=CLONE_CHILD_CLEARTID|CLONE_CHILD_SETTID|SIGCHLD)
pthread_create()  clone(flags=CLONE_VM|CLONE_FS|CLONE_FILES|CLONE_SIGHAND|CLONE_THREAD|...)
```

CLONE_VM 表示共享地址空间，CLONE_FILES 表示共享文件描述符表，CLONE_THREAD 表示加入创建者的线程组。没有这些标志时，子进程得到一份地址空间的副本（[写时复制](计算机操作系统%20-%20内存管理.md#分页系统地址映射)），修改全局变量不影响父进程；有这些标志时，新线程修改的就是同一个变量。getpid() 返回的是线程组 ID，同一进程中的线程都相同，gettid() 返回每个线程自己的 ID，top -H、ps -L 中看到的就是它。

fork 调用一次、返回两次：父进程中返回子进程的 PID，子进程中返回 0。多线程的进程 fork 后，子进程中只有调用 fork 的那个线程。

<div align="center"> <img src="pics/process-vs-thread.png" width="760px"/> </div><br>

因此选择多进程还是多线程，主要看更需要隔离还是共享：

- 任务之间需要隔离、一个出错不能拖垮其它任务时用多进程，例如 Chrome 把网页放在单独的渲染进程中，一个网页崩溃不影响浏览器和其它标签页；执行不受信任的代码（例如 Agent 运行模型生成的脚本）也应该放在单独的进程甚至容器中；
- 任务之间要频繁共享数据、对创建和切换的开销敏感时用多线程，例如 Web 服务器用线程池处理请求，各线程直接读写同一份本地缓存。

### 4. 上下文切换

上下文切换指的是 CPU 从执行一个线程改为执行另一个线程时，把当前线程的寄存器、程序计数器、栈指针等保存起来，再恢复另一个线程上次保存的值。以下情况会发生上下文切换：

- 时间片用完，被调度程序换下；
- 线程主动阻塞，例如等待 I/O、等待锁、调用 sleep()；
- 更高优先级的线程进入就绪状态。

需要注意的是，系统调用只是从用户态进入内核态，执行完后通常回到同一个线程，不一定发生上下文切换。

同一进程中的线程切换不需要换地址空间；切换到另一个进程时还要切换页表，TLB 和 CPU 缓存中原来的地址映射和数据大多用不上，要重新加载，这部分间接开销通常比保存寄存器更大。x86 的 PCID 可以给 TLB 表项标上所属的地址空间，切换页表时不必清空整个 TLB，没有 PCID 时，每次切换页表都会清空 TLB 中除全局页（内核映射）以外的表项。

例如把两个执行流固定在同一个 CPU 上，通过两根管道来回传 1 个字节，让它们交替运行，两个线程之间、两个进程之间每次切换都约 1.1 微秒，其中还包含一次 write 和一次 read 系统调用（Linux 实测，见[附录 A1](#a1-上下文切换)）。数据量很小时两者几乎没有差别，进程切换的额外开销主要在工作集较大时体现出来。线程过多、频繁阻塞时，CPU 会把相当一部分时间花在切换上，可以用 vmstat 的 cs 列或 pidstat -w 观察每秒的切换次数。

线程也不能无限创建：Linux 上受 ulimit -u、/proc/sys/kernel/threads-max 和 pid_max 限制，超出时 Java 抛出 OutOfMemoryError: unable to create native thread（见[附录 A5](#a5-线程数的上限)）。

### 5. 协程 🔥🔥

协程（Coroutine）是在用户态实现的轻量级线程，由程序自己调度，而不是由操作系统内核调度。协程在等待 I/O 时主动让出执行权，运行时再把其它协程调度到同一个线程上执行。

协程要解决的是高并发 I/O 的写法问题：用 [epoll](Socket.md#epoll) 时少量线程就能处理几万个连接，但处理逻辑要拆成一段段回调；协程让代码仍按阻塞的方式顺序写，运行时在底层改用非阻塞 I/O 和 epoll 这类多路复用接口，等待时挂起协程，就绪后再恢复。

Go 和 Java 虚拟线程把大量协程映射到运行时创建的少量线程（通常与 CPU 核数相当）上，称为 M:N 调度；Python 的 asyncio 则在一个线程的事件循环中轮流执行所有协程。大多数协程是协作式调度的，只在让出点切换，例如等待 I/O、等待锁、sleep；一个协程长时间计算而不让出，就会一直占住所在的线程。

Go 的 GMP 模型是一个典型实现：G 是 goroutine，M 是系统线程，P 是执行 Go 代码需要的处理器，数量默认等于可用的 CPU 核数。每个 P 有自己的就绪队列，M 绑定一个 P 后从队列中取 G 执行，队列空了就从其它 P 的队列中偷取一半。Go 1.14 起运行时还会用信号打断长时间运行的 goroutine（异步抢占），避免没有函数调用的循环一直占住线程。

与线程相比：

- 切换在用户态完成，只需要保存少量寄存器，不需要陷入内核，开销小，例如 goroutine 每次切换约 0.1～0.2 微秒，虚拟线程约 0.3 微秒，线程约 1.1 微秒（测法不同，只比较数量级，见[附录 A6](#a6-协程的切换开销)、[附录 A1](#a1-上下文切换)）；
- 占用的内存少，可以同时存在大量协程，而每个线程都要预留独立的栈，例如 Linux x64 上 Java 线程的栈默认为 1 MB（ARM64 的 Linux 和 macOS 上为 2 MB），线程数量有限；
- 同一个线程上的协程不能并行执行，要利用多核仍然需要多个线程；协程中如果执行了运行时没有改写的阻塞系统调用（例如读本地文件），所在的线程仍会被阻塞。

协程按是否有自己的调用栈分为两类。有栈协程（stackful）可以在任意深度的函数调用中挂起，挂起时保存整个调用栈，例如 goroutine 和 Java 的虚拟线程；无栈协程（stackless）由编译器把 async 函数改写成状态机，只能在 await 处挂起，局部变量保存在状态对象中，例如 Python 的 async/await 和 Kotlin 协程。无栈协程更省内存，但 async 会沿调用链传染，调用它的函数也要写成 async。

Java 21 正式引入的虚拟线程（[JEP 444](https://openjdk.org/jeps/444)）就是 JVM 实现的协程：虚拟线程由 JVM 调度到少量的平台线程（称为载体线程，carrier thread）上运行，执行阻塞 I/O 时从平台线程上卸载，让平台线程去执行其它虚拟线程。调度器是一个工作窃取的 ForkJoinPool，平台线程数默认等于 CPU 核数，JDK 21 不按时间片抢占虚拟线程。

虚拟线程卸载时，它的栈帧以栈块对象（stack chunk）的形式保存在堆中，等 I/O 就绪后再挂载到某个平台线程上继续执行，所以阻塞的虚拟线程只占用与调用深度相当的堆内存，不占用平台线程。虚拟线程的创建成本很低，不需要用线程池复用，需要限制并发数时使用信号量。在 JDK 21 中，虚拟线程在 synchronized 块内阻塞时无法卸载，会固定（pinning）在载体线程上，所以锁内有阻塞操作时改用 ReentrantLock（见 [Java 并发](Java%20并发.md#使用选择)）；JDK 24 起（[JEP 491](https://openjdk.org/jeps/491)）基本消除了这个限制。

<div align="center"> <img src="pics/virtual-thread-unmount.png" width="760px"/> </div><br>

例如在 JDK 21 中启动 1 万个阻塞在同一个 CountDownLatch 上的线程（Ubuntu 24.04 容器实测，见[附录 A2](#a2-平台线程与虚拟线程的开销)）：

- 平台线程用时约 1.4 秒，进程的常驻内存增加约 290 MB，平均每个约 30 KB，这是因为 2 MB（aarch64）的栈只是预留的虚拟地址，用到的页才占用物理内存；
- 虚拟线程用时约 30 毫秒，每个只在堆中占用约 2 KB；启动 100 万个虚拟线程用时约 0.5 秒，堆中共占用约 690 MB。

协程也不能无限创建：每个协程的栈和状态都要占内存，例如把最大堆设为 256 MB 时，启动 100 万个阻塞的虚拟线程会抛出 OutOfMemoryError。协程适合大量任务都在等待 I/O 的场景，例如每个请求都要调用下游接口、查询数据库；CPU 密集的任务没有等待可以让出，开再多协程也只能由少量线程轮流执行，不会更快。

## 进程状态的切换

<div align="center"> <img src="pics/process-states.png" width="720px"/> </div><br>

- 新建状态（new）：正在创建，PCB 已建立但还没有进入就绪队列；
- 就绪状态（ready）：等待被调度；
- 运行状态（running）：正在 CPU 上执行；
- 阻塞状态（waiting）：等待资源；
- 终止状态（terminated）：已经退出，等待父进程回收。

应该注意以下内容：

- 只有就绪态和运行态可以相互转换，其它的都是单向转换。就绪状态的进程通过调度算法从而获得 CPU 时间，转为运行状态；而运行状态的进程，在分配给它的 CPU 时间片用完之后就会转为就绪状态，等待下一次调度；
- 阻塞状态是缺少需要的资源从而由运行状态转换而来，但是该资源不包括 CPU 时间，缺少 CPU 时间会从运行态转换为就绪态。

Linux 的进程状态和僵尸进程、孤儿进程见 [Linux](Linux.md#进程状态)，Java 线程的 6 种状态见 [Java 并发](Java%20并发.md#六线程状态)。

## 进程调度算法

不同环境的调度算法目标不同，因此需要针对不同环境来讨论调度算法。

### 1. 批处理系统

批处理系统没有太多的用户操作，在该系统中，调度算法目标是保证吞吐量和周转时间（从提交到终止的时间）。

##### 1.1 先来先服务（First-Come First-Served, FCFS）

非抢占式的调度算法，按照请求的顺序进行调度。

有利于长作业，但不利于短作业，因为短作业必须一直等待前面的长作业执行完毕才能执行，而长作业又需要执行很长时间，造成了短作业等待时间过长。

##### 1.2 短作业优先（Shortest Job First, SJF）

非抢占式的调度算法，按估计运行时间最短的顺序进行调度。

长作业有可能会饿死，处于一直等待短作业执行完毕的状态。因为如果一直有短作业到来，那么长作业永远得不到调度。

例如 A、B、C 同时到达，分别需要运行 8、4、1 个单位时间：FCFS 按 A、B、C 执行，平均等待 (0 + 8 + 12) / 3 ≈ 6.7；SJF 按 C、B、A 执行，平均等待 (0 + 1 + 5) / 3 = 2。所有作业同时到达时，SJF 的平均等待时间最短。

##### 1.3 最短剩余时间优先（Shortest Remaining Time Next, SRTN）

最短作业优先的抢占式版本，按剩余运行时间的顺序进行调度。当一个新的作业到达时，其整个运行时间与当前进程的剩余时间作比较。如果新的进程需要的时间更少，则挂起当前进程，运行新的进程。否则新的进程等待。

### 2. 交互式系统

交互式系统有大量的用户交互操作，在该系统中调度算法的目标是快速地进行响应。

##### 2.1 时间片轮转

将所有就绪进程按 FCFS 的原则排成一个队列，每次调度时，把 CPU 时间分配给队首进程，该进程可以执行一个时间片。当时间片用完时，由计时器发出时钟中断，调度程序便停止该进程的执行，并将它送往就绪队列的末尾，同时继续把 CPU 时间分配给队首的进程。

时间片轮转算法的效率和时间片的大小有很大关系：

- 因为进程切换都要保存进程的信息并且载入新进程的信息，如果时间片太小，会导致进程切换得太频繁，在进程切换上就会花过多时间；
- 而如果时间片过长，那么实时性就不能得到保证。

<div align="center"> <img src="pics/process-rr.png" width="740px"/> </div><br>

##### 2.2 优先级调度

为每个进程分配一个优先级，按优先级进行调度。

为了防止低优先级的进程永远等不到调度，可以随着时间的推移增加等待进程的优先级。

##### 2.3 多级反馈队列

一个进程需要执行 100 个时间片，如果采用时间片轮转调度算法，那么需要被调度 100 次。

多级反馈队列是为这种需要连续执行多个时间片的进程考虑，它设置了多个队列，每个队列时间片大小都不同，例如 1、2、4、8……进程在第一个队列没执行完，就会被移到下一个队列。这种方式下，之前的进程只需要被调度 7 次（1 + 2 + … + 64 = 127 ≥ 100）。

每个队列优先权也不同，最上面的优先权最高。因此只有上一个队列没有进程在排队，才能调度当前队列上的进程。

可以将这种调度算法看成是时间片轮转调度算法和优先级调度算法的结合。交互式进程经常没用完时间片就因等待 I/O 让出 CPU，一直留在高优先级队列，响应快；计算密集的进程则逐级下沉。

### 3. 实时系统

实时系统要求一个请求在一个确定时间内得到响应。

分为硬实时和软实时，前者必须满足绝对的截止时间，后者可以容忍一定的超时。

实际的操作系统会组合使用这些思想。例如 Linux 2.6.23 起的完全公平调度器（CFS）给每个进程记录按优先级加权后的虚拟运行时间，总是选择虚拟运行时间最小的进程运行，让各进程按权重分享 CPU；Linux 6.6 起开始改用 EEVDF 调度器，在公平分享的基础上考虑每个进程的截止时间，让对延迟敏感的进程更快得到运行。实时进程使用单独的 SCHED_FIFO、SCHED_RR 策略，优先于普通进程。

## 进程同步

### 1. 临界区

临界资源指的是一次只允许一个进程使用的资源，例如共享变量、打印机；对临界资源进行访问的那段代码称为临界区。

例如两个进程对共享变量 count 执行 count++，这条语句分为读到寄存器、加 1、写回内存三步。count 为 5 时按下面的顺序交错执行，结果是 6 而不是 7：

```text
时刻  进程 A              进程 B              内存中的 count
1     读 count，得到 5                        5
2                         读 count，得到 5    5
3     加 1，得到 6                            5
4     写回 6                                  6
5                         加 1，得到 6        6
6                         写回 6              6
```

为了互斥访问临界资源，每个进程在进入临界区之前，需要先进行检查。

```c
// entry section
// critical section;
// exit section
```

### 2. 同步与互斥

- 同步：多个进程因为合作产生的直接制约关系，使得进程有一定的先后执行关系；
- 互斥：多个进程在同一时刻只有一个进程能进入临界区。

### 3. 信号量

信号量（Semaphore）是一个整型变量，可以对其执行 down 和 up 操作，也就是常见的 P 和 V 操作。

- down：如果信号量大于 0，执行 -1 操作；如果信号量等于 0，进程睡眠，等待信号量大于 0；
- up：对信号量执行 +1 操作，唤醒睡眠的进程让其完成 down 操作。

down 和 up 操作需要被设计成原语，不可分割。单处理器上通常在执行这些操作时屏蔽中断；多处理器上屏蔽中断只对本 CPU 有效，还要用 TSL、CAS 这类原子指令保护信号量。

如果信号量的取值只能为 0 或者 1，就称为二值信号量，可以当作互斥量（Mutex）使用，0 表示临界区已经加锁，1 表示临界区解锁。需要注意的是，信号量可以由另一个进程执行 up，而 pthread_mutex、ReentrantLock 这类互斥锁只能由加锁的线程释放，所以后面读者-写者问题中由第一个读者 down、最后一个读者 up 的 data_mutex 不能换成互斥锁。

```c
typedef int semaphore;
semaphore mutex = 1;
void P1() {
    down(&mutex);
    // 临界区
    up(&mutex);
}

void P2() {
    down(&mutex);
    // 临界区
    up(&mutex);
}
```

使用信号量实现生产者-消费者问题：

问题描述：使用一个缓冲区来保存物品，只有缓冲区没有满，生产者才可以放入物品；只有缓冲区不为空，消费者才可以拿走物品。

因为缓冲区属于临界资源，因此需要使用一个互斥量 mutex 来控制对缓冲区的互斥访问。

为了同步生产者和消费者的行为，需要记录缓冲区中物品的数量。数量可以使用信号量来进行统计，这里需要使用两个信号量：empty 记录空缓冲区的数量，full 记录满缓冲区的数量。其中，empty 信号量是在生产者进程中使用，当 empty 不为 0 时，生产者才可以放入物品；full 信号量是在消费者进程中使用，当 full 信号量不为 0 时，消费者才可以取走物品。

需要注意的是，down(empty) 必须放在 down(mutex) 之前。如果顺序反过来，缓冲区满时生产者先拿到 mutex，再在 down(empty) 上睡眠；消费者取物品之前要先拿 mutex，也被挡住，于是没有进程能执行 up(empty)，两者永远等待下去。

```c
#define N 100
typedef int semaphore;
semaphore mutex = 1;
semaphore empty = N;
semaphore full = 0;

void producer() {
    while(TRUE) {
        int item = produce_item();
        down(&empty);
        down(&mutex);
        insert_item(item);
        up(&mutex);
        up(&full);
    }
}

void consumer() {
    while(TRUE) {
        down(&full);
        down(&mutex);
        int item = remove_item();
        consume_item(item);
        up(&mutex);
        up(&empty);
    }
}
```

### 4. 管程

使用信号量机制实现的生产者消费者问题需要客户端代码做很多控制，而管程把控制的代码独立出来，不仅不容易出错，也使得客户端代码调用更容易。

C 语言不支持管程，下面的示例代码使用了类 Pascal 语言来描述管程。示例代码的管程提供了 insert() 和 remove() 方法，客户端代码通过调用这两个方法来解决生产者-消费者问题。

```pascal
monitor ProducerConsumer
    integer i;
    condition c;

    procedure insert();
    begin
        // ...
    end;

    procedure remove();
    begin
        // ...
    end;
end monitor;
```

管程有一个重要特性：在一个时刻只能有一个进程使用管程。进程在无法继续执行的时候不能一直占用管程，否则其它进程永远不能使用管程。

管程引入了条件变量以及相关的操作 wait() 和 signal() 来实现同步操作。对条件变量执行 wait() 操作会导致调用进程阻塞，把管程让出来给另一个进程持有。signal() 操作用于唤醒被阻塞的进程。

使用管程实现生产者-消费者问题：

```pascal
// 管程
monitor ProducerConsumer
    condition full, empty;
    integer count := 0;

    procedure insert(item: integer);
    begin
        if count = N then wait(full);
        insert_item(item);
        count := count + 1;
        if count = 1 then signal(empty);
    end;

    function remove: integer;
    begin
        if count = 0 then wait(empty);
        remove = remove_item;
        count := count - 1;
        if count = N -1 then signal(full);
    end;
end monitor;

// 生产者客户端
procedure producer
begin
    while true do
    begin
        item = produce_item;
        ProducerConsumer.insert(item);
    end
end;

// 消费者客户端
procedure consumer
begin
    while true do
    begin
        item = ProducerConsumer.remove;
        consume_item(item);
    end
end;
```

上面的伪代码用 if 检查条件，前提是被 signal 唤醒的进程立即运行。Java 的每个对象都可以当作管程，synchronized 保证互斥，wait()、notify() 相当于条件变量的 wait 和 signal，但被唤醒的线程要重新竞争锁，条件可能已经变了，所以要用 while 检查（见 [Java 并发](Java%20并发.md#wait-notify-notifyall)）。

## 经典同步问题

生产者和消费者问题前面已经讨论过了。

### 1. 哲学家进餐问题

<div align="center"> <img src="pics/philosophers.png" width="720px"/> </div><br>

五个哲学家围着一张圆桌，每个哲学家面前放着食物。哲学家的生活有两种交替活动：吃饭以及思考。当一个哲学家吃饭时，需要先拿起自己左右两边的两根筷子，并且一次只能拿起一根筷子。

下面是一种错误的解法，如果所有哲学家同时拿起左手边的筷子，那么所有哲学家都在等待其它哲学家吃完并释放自己手中的筷子，导致死锁。

```c
#define N 5

void philosopher(int i) {
    while(TRUE) {
        think();
        take(i);       // 拿起左边的筷子
        take((i+1)%N); // 拿起右边的筷子
        eat();
        put(i);
        put((i+1)%N);
    }
}
```

为了防止死锁的发生，可以设置两个条件：

- 必须同时拿起左右两根筷子；
- 只有在两个邻居都没有进餐的情况下才允许进餐。

```c
#define N 5
#define LEFT (i + N - 1) % N // 左邻居
#define RIGHT (i + 1) % N    // 右邻居
#define THINKING 0
#define HUNGRY   1
#define EATING   2
typedef int semaphore;
int state[N];                // 跟踪每个哲学家的状态
semaphore mutex = 1;         // 临界区的互斥，临界区是 state 数组，对其修改需要互斥
semaphore s[N];              // 每个哲学家一个信号量

void philosopher(int i) {
    while(TRUE) {
        think(i);
        take_two(i);
        eat(i);
        put_two(i);
    }
}

void take_two(int i) {
    down(&mutex);
    state[i] = HUNGRY;
    check(i);
    up(&mutex);
    down(&s[i]); // 只有收到通知之后才可以开始吃，否则会一直等下去
}

void put_two(int i) {
    down(&mutex);
    state[i] = THINKING;
    check(LEFT); // 尝试通知左右邻居，自己吃完了，你们可以开始吃了
    check(RIGHT);
    up(&mutex);
}

// 检查两个邻居是否都没有用餐，如果是的话，就 up(&s[i])，使得 down(&s[i]) 能够得到通知并继续执行
void check(int i) {
    if(state[i] == HUNGRY && state[LEFT] != EATING && state[RIGHT] !=EATING) {
        state[i] = EATING;
        up(&s[i]);
    }
}
```

### 2. 读者-写者问题

允许多个进程同时对数据进行读操作，但是不允许读和写以及写和写操作同时发生。

一个整型变量 count 记录在对数据进行读操作的进程数量，一个互斥量 count_mutex 用于对 count 加锁，一个二值信号量 data_mutex 用于对读写的数据加锁。

```c
typedef int semaphore;
semaphore count_mutex = 1;
semaphore data_mutex = 1;
int count = 0;

void reader() {
    while(TRUE) {
        down(&count_mutex);
        count++;
        if(count == 1) down(&data_mutex); // 第一个读者需要对数据进行加锁，防止写进程访问
        up(&count_mutex);
        read();
        down(&count_mutex);
        count--;
        if(count == 0) up(&data_mutex);
        up(&count_mutex);
    }
}

void writer() {
    while(TRUE) {
        down(&data_mutex);
        write();
        up(&data_mutex);
    }
}
```

这种实现在读者源源不断时可能导致写者饥饿，写者优先和按到达顺序排队的公平实现见[进阶：读者-写者问题](计算机操作系统%20-%20进程管理%20-%20进阶.md#读者-写者问题)。

## 进程通信 🔥🔥

进程同步与进程通信很容易混淆，它们的区别在于：

- 进程同步：控制多个进程按一定顺序执行；
- 进程通信：进程间传输信息。

进程通信是一种手段，而进程同步是一种目的：为了让进程按顺序执行，需要通过通信传递同步所需的信息。

| 方式 | 传递的内容 | 特点 | 例子 |
| --- | --- | --- | --- |
| 管道 | 字节流 | 单向，一般用于有亲缘关系的进程 | shell 中的 ps aux \| grep java |
| FIFO | 字节流 | 有路径名，不相关的进程也能使用 | 本机的客户进程和服务器进程 |
| 消息队列 | 带类型的消息 | 保留消息边界，可以按类型读取 | 多个进程向同一个队列投递任务 |
| 共享存储 | 直接读写同一块内存 | 最快，需要自己同步 | 大量数据的交换 |
| 信号量 | 不传数据 | 计数器，用于同步和互斥 | 配合共享存储 |
| 信号 | 信号编号（sigqueue 可附带一个整数） | 异步通知 | kill、[SIGCHLD](Linux.md#sigchld) |
| 套接字 | 字节流或数据报 | 可以跨机器 | 网络服务、Unix 域套接字 |

### 1. 管道

管道是通过调用 pipe 函数创建的，fd[0] 用于读，fd[1] 用于写。

```c
#include <unistd.h>
int pipe(int fd[2]);
```

它具有以下限制：

- 数据只能单向流动，双向通信要建两根管道；
- 管道没有名字，一般靠 fork 继承文件描述符，所以通常用于父子、兄弟这类有共同祖先的进程。

<div align="center"> <img src="pics/pipe.png" width="740px"/> </div><br>

fork 后父子进程要关闭各自不用的一端：只要还有一个写端没关闭，读完数据的 read 就会一直阻塞，所有写端都关闭后 read 才返回 0。管道容量有限（Linux 默认 16 页，页大小为 4 KB 时是 64 KB），写满时 write 也会阻塞。

### 2. FIFO

也称为命名管道，它有一个路径名，不相关的进程打开同一个路径就能通信。

```c
#include <sys/stat.h>
int mkfifo(const char *path, mode_t mode);
int mkfifoat(int fd, const char *path, mode_t mode);
```

FIFO 常用于客户-服务器应用程序中，FIFO 用作汇聚点，在客户进程和服务器进程之间传递数据。

<div align="center"> <img src="pics/fifo.png" width="720px"/> </div><br>

### 3. 消息队列

消息队列是保存在内核中的消息链表。相比于 FIFO，消息队列具有以下优点：

- 消息队列可以独立于读写进程存在，写进程退出后消息仍然保留，而 FIFO 的读写端都关闭后，未读的数据就丢弃了；
- 按消息读写，保留消息的边界，而 FIFO 是字节流，接收方要自己拆分；
- 读进程可以根据消息类型有选择地接收消息，而不像 FIFO 那样只能按顺序接收。

每条消息都要在进程和内核之间复制两次，不适合传输大量数据。

### 4. 信号量

它是一个计数器，用于为多个进程提供对共享数据对象的访问，P、V 操作与[信号量](#3-信号量)一节相同。

### 5. 共享存储

允许多个进程共享一个给定的存储区。因为数据不需要在进程之间复制，所以这是最快的一种 IPC。

管道每传一次数据要复制两次：write 把数据从写进程复制到内核缓冲区，read 再复制到读进程。共享内存把同一个物理页框映射到两个进程的地址空间，写进程写入后，读进程直接就能读到。

<div align="center"> <img src="pics/ipc-shm.png" width="740px"/> </div><br>

共享内存本身不提供同步，读进程不知道数据什么时候写完，多个进程同时写也会互相覆盖，因此需要配合信号量使用。

例如用 POSIX 共享内存把一条 1 KB 以内的消息交给另一个进程，依次调用 shm_open 创建共享内存对象、ftruncate 设置大小、mmap 映射到地址空间，读写完后 munmap 解除映射、shm_unlink 删除对象。信号量放在共享内存中，sem_init 的第二个参数为 1 表示在进程间共享（Linux 上编译运行，见[附录 A3](#a3-posix-共享内存)）：

```c
struct msg {
    sem_t ready;        // 写完后 up，读进程 down 等待
    char data[1024];
};

int main(void) {
    int fd = shm_open("/demo_shm", O_CREAT | O_RDWR, 0600);
    ftruncate(fd, sizeof(struct msg));
    struct msg *m = mmap(NULL, sizeof(struct msg), PROT_READ | PROT_WRITE, MAP_SHARED, fd, 0);
    sem_init(&m->ready, 1, 0);

    if (fork() == 0) {                                         // 写进程
        snprintf(m->data, sizeof m->data, "order 1024 paid");  // 直接写共享内存
        sem_post(&m->ready);
        return 0;
    }
    sem_wait(&m->ready);                                       // 读进程等待写完
    printf("读到：%s\n", m->data);
    wait(NULL);
    munmap(m, sizeof(struct msg));
    shm_unlink("/demo_shm");
    return 0;
}
```

这里为了简短用 fork 创建写进程，没有亲缘关系的进程只要用同一个名字调用 shm_open，就能映射到同一块共享内存。

多个进程也可以将同一个文件映射到它们的地址空间从而实现共享内存。另外 XSI 共享内存（shmget、shmat）不是使用文件，而是使用内存的匿名段。

### 6. 套接字

与其它通信机制不同的是，它可用于不同机器间的进程通信。

同一台机器上还可以用 Unix 域套接字（AF_UNIX），它以文件路径为地址，不经过网络协议栈，例如 Docker 客户端通过 /var/run/docker.sock 访问守护进程。

### A4 fork 与 pthread_create 的 clone 标志

Docker Desktop 中的 Ubuntu 24.04 容器（aarch64），gcc 13.3，strace 6.8。程序先 fork 一个子进程，子进程把全局变量 counter 加 1；再用 pthread_create 创建一个线程，线程也把 counter 加 1：

```c
int counter = 0;
static void *worker(void *arg) {
    counter++;
    printf("线程  pid=%d tid=%d\n", getpid(), gettid());
    return NULL;
}
// main 中：
pid_t c = fork();
if (c == 0) { counter++; printf("子进程 pid=%d tid=%d\n", getpid(), gettid()); _exit(0); }
waitpid(c, NULL, 0);
printf("fork 之后 counter=%d\n", counter);
pthread_create(&t, NULL, worker, NULL);
pthread_join(t, NULL);
printf("线程结束后 counter=%d\n", counter);
```

$ strace -f -e trace=clone,clone3 ./pt

### A5 线程数的上限

macOS 15.8（Apple M1 Pro），Temurin JDK 21.0.13。不断创建阻塞在同一个 CountDownLatch 上的线程，直到失败：

```java
for (;; n++) new Thread(() -> { try { gate.await(); } catch (InterruptedException e) { } }).start();
```

```text
$ sysctl kern.num_taskthreads
kern.num_taskthreads: 8192
$ java ManyThreads.java
[3.588s][warning][os,thread] Failed to start thread "Unknown thread" - pthread_create failed (EAGAIN) for attributes: stacksize: 2048k, guardsize: 16k, detached.
创建了 8163 个线程后：java.lang.OutOfMemoryError: unable to create native thread: possibly out of memory or process/resource limits reached
```

macOS 限制每个进程最多 8192 个线程，其余约 30 个是 JVM 自己的线程。Linux 上的限制见 [pthread_create(3)](https://man7.org/linux/man-pages/man3/pthread_create.3.html) 的 EAGAIN 一项。

### A6 协程的切换开销

macOS 15.8（Apple M1 Pro），Go 1.27.3、Temurin JDK 21.0.13。与附录 A1 相同，两个执行流来回传递数据，只用一个线程执行：Go 用两个无缓冲 channel，GOMAXPROCS=1（同时执行 Go 代码的线程只有一个，没有固定 CPU）；Java 用两个 SynchronousQueue，调度器只有一个平台线程。各执行 200 万个来回：

```go
go func() { for i := 0; i < n; i++ { b <- <-a } }()
for i := 0; i < n; i++ { a <- 1; <-b }
fmt.Printf("goroutine 每次切换约 %.0f ns\n", ns/n/2)
```

```java
Thread peer = Thread.ofVirtual().start(() -> { for (int i = 0; i < n; i++) b.put(a.take()); });
// 另一个虚拟线程中（省略了 InterruptedException 的处理）：
for (int i = 0; i < n; i++) { a.put(1); b.take(); }
```

```text
$ for i in 1 2 3; do GOMAXPROCS=1 go run pingpong.go; done
goroutine 每次切换约 113 ns
goroutine 每次切换约 117 ns
goroutine 每次切换约 115 ns
$ java -Djdk.virtualThreadScheduler.parallelism=1 -Djdk.virtualThreadScheduler.maxPoolSize=1 VtPingPong
virtual 每次切换约 274 ns
virtual 每次切换约 252 ns
virtual 每次切换约 271 ns
```

机器负载较高时 goroutine 测到 130～190 ns，虚拟线程 240～380 ns。耗时中包含 channel 或队列本身的操作；与附录 A1 的操作系统不同（A1 是 Linux 容器），只能比较数量级。
