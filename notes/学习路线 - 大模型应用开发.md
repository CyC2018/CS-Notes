## 一、说明

适合会一门编程语言（Python 或 Java）、准备大模型应用开发面试的读者，每天约 1～1.5 小时。动手部分需要一个兼容 OpenAI 接口的模型服务（例如 DeepSeek）或本地的 Qwen2.5 小模型；学过 Java 后端路线的读者可以跳过算法题。

每天先读完阅读范围，再不看笔记回答自测题，答完展开参考要点核对；动手练习对照预期的结果。自测答得上来、动手结果与预期一致、算法题提交通过，这一天就完成了。选读可以跳过。

## 二、开始之前

本路线不讲语法。动手部分大多用 Python，开始前先确认能独立写出下面 5 个程序：

1. 调用 https://api.github.com/repos/CyC2018/CS-Notes ，解析返回的 JSON，打印 stargazers_count；
2. 读取一个 JSON Lines 文件（每行一个订单，含 user_id 和 amount），统计每个用户的订单数和总金额，写入 JSON 文件；
3. 把一段长文本切成不超过 200 字的片段，只在句号处切分；
4. 用列表保存对话历史，只保留最近 10 条消息；
5. 请求超时时重试，最多 3 次，每次等待的时间翻倍。

写不出来的，先补对应的语法：HTTP 请求与 JSON、文件读写、字符串、列表、异常与循环。用 Java 写同样的程序也可以。

### 第 1 天：Token 与 Transformer

Token 是模型处理文本的单位，也是计费和上下文长度的单位。Transformer 一节先看整体结构，再看参数分布在哪里；混合专家可以略读。

阅读：《大模型应用》从[Token 与分词](大模型应用.md#token-与分词)读到[Transformer 结构](大模型应用.md#transformer-结构)。

自测：

1. Transformer 的结构是怎样的？（见[整体结构](大模型应用.md#1-整体结构)）
2. 大模型的参数主要分布在哪里？（见[参数都在哪里](大模型应用.md#2-参数都在哪里)）
3. 什么是 Token？同样的内容，中文和英文的 Token 数一样吗？（见[Token 与分词](大模型应用.md#token-与分词)）

<details>
<summary>参考要点</summary>

1. 目前的大模型基本是只保留解码器的 Decoder-only 结构；Token 经词嵌入变成向量（Qwen2.5-7B 为 3584 维），依次经过几十个相同的层（28 层），每层先用注意力从前文收集信息，再用前馈网络逐位置加工；子层都带残差连接和归一化（多为 Pre-Norm 的 RMSNorm）；最后一个位置经线性层得到 logits，softmax 后得到下一个 Token 的概率。
2. 几乎都在矩阵中：每层的注意力和前馈网络，以及词嵌入和输出层（Qwen2.5-7B 中各约 7%）；Qwen2.5-7B 的前馈网络三个矩阵（3584 → 18944 → 3584）占全部参数的 75%；GQA 使 k_proj、v_proj 只有 q_proj 的七分之一，总计约 76 亿个参数。
3. Token 是分词器切出的文本片段，模型只处理它在词表中的编号，常用字节级 BPE 反复合并最高频的相邻片段；上下文窗口和费用都按 Token 计算；中英文不同，DeepSeek 估算 1 个中文字符约 0.6 个 Token、1 个英文字符约 0.3 个，准确数量以 usage 为准。

</details>

动手：下载 Qwen2.5-7B-Instruct 的 config.json，按[参数都在哪里](大模型应用.md#2-参数都在哪里)一节的方法算出一层中注意力和前馈网络的参数量，再与[附录 A16](大模型应用.md#a16-qwen25-7b-与-qwen3-30b-a3b-的参数量)对照。

预期：每层注意力 29,364,736 个参数（含 q、k、v 的偏置 4,608 个）、前馈网络 203,685,888 个（加两个 RMSNorm 共 233,057,792 个），28 层、两个嵌入加最后的归一化共 7,615,616,512 个，与附录 A16 一致。

算法（哈希表，简单）：[1. 两数之和](https://leetcode.cn/problems/two-sum/)，题解见[数组中两个数的和为给定值](Leetcode%20题解%20-%20哈希表.md#1-数组中两个数的和为给定值)。

### 第 2 天：注意力机制

注意力是 Transformer 的核心，对着“饿”的例子把 Q、K、V 的计算走一遍。注意力本身不区分先后，位置编码一段看 RoPE 怎样让分数只取决于内容和相对距离。计算量与 FlashAttention 一节说明上下文变长后注意力的开销怎样增长；FlashAttention 结果不变，省的是显存读写。

阅读：《大模型应用》的[注意力机制](大模型应用.md#注意力机制)。选读：[进阶：注意力机制](大模型应用%20-%20进阶.md#注意力机制)。

自测：

1. 注意力的计算公式是什么？为什么要除以 √d？（见[注意力机制](大模型应用.md#注意力机制)）
2. 多头注意力有什么作用？（见[多头注意力](大模型应用.md#1-多头注意力)）
3. FlashAttention 解决了什么问题？（见[计算量与 FlashAttention](大模型应用.md#2-计算量与-flashattention)）

<details>
<summary>参考要点</summary>

1. 公式为 softmax(QK<sup>T</sup> / √d) V：Q 与各 K 点积得到分数，softmax 成权重后对 V 加权求和；分量独立、均值 0、方差 1 时点积的方差为 d，维度大时 softmax 几乎集中到一个 Token 上，梯度接近 0；除以 √d 使方差恢复为 1。
2. 单头注意力中每个 Token 只有一组权重，只能按一种标准挑选信息；多头把 Q、K、V 切成 h 份分别计算，拼接后乘 W<sub>O</sub>，不同的头可以关注指代、相邻词等不同关系；每头维度为 d / h，计算量与单头基本相同。
3. 标准注意力的计算量为 O(n<sup>2</sup>d)，n × n 的分数矩阵占 O(n<sup>2</sup>) 显存，长上下文时显存读写成为瓶颈；FlashAttention 分块在 GPU 片上缓存中计算，分数矩阵不写回显存，用在线 softmax 逐块累积；结果在数学上与标准注意力相同，不是近似，省的是显存读写而不是计算量。

</details>

### 第 3 天：生成、KV Cache 与采样

模型每次只生成一个 Token。KV Cache 避免重复计算前面 Token 的 K 和 V，代价是占用显存，它的大小决定了一张显卡能同时服务多少请求。采样参数决定每一步怎样从概率分布中选出 Token。

阅读：《大模型应用》从[自回归生成与 KV Cache](大模型应用.md#自回归生成与-kv-cache)读到[采样参数](大模型应用.md#采样参数)。选读：[进阶：自回归生成与 KV Cache](大模型应用%20-%20进阶.md#自回归生成与-kv-cache)。

自测：

1. KV Cache 是什么？为什么能加快生成？（见[自回归生成与 KV Cache](大模型应用.md#自回归生成与-kv-cache)）
2. MHA、MQA 和 GQA 有什么区别？（见[自回归生成与 KV Cache](大模型应用.md#自回归生成与-kv-cache)）
3. temperature 和 top-p 分别控制什么？（见[采样参数](大模型应用.md#采样参数)）

<details>
<summary>参考要点</summary>

1. 因果掩码下前文 Token 的 K、V 不再变化，缓存起来复用就是 KV Cache；预填充一次算好输入的 K、V，解码每步只为新 Token 计算 Q、K、V，再与缓存做注意力，不再重算前文；代价是显存，Qwen2.5-7B 每个 Token 56 KB，32K Token 约 1.75 GB。
2. MHA 中每个查询头都有自己的 K、V；GQA 让多个查询头共享一组 K、V，Qwen2.5-7B 的 28 个查询头共享 4 组，每个 Token 缓存 56 KB，MHA 要 392 KB；MQA 中所有查询头共享一组，缓存最小，但效果下降更明显；GQA 减少的是缓存和解码每步读取的数据量，计算量基本不变，每个查询头仍有自己的 Q，所以效果接近 MHA。
3. temperature 把分数除以 T 再 softmax，T < 1 时分布更尖、T > 1 时更平，例如最高概率 0.50 在 T = 0.5 时升到 0.75；top-p 只在累计概率刚达到 p 的高概率 Token 中采样，候选数随分布变化；抽取字段、调用工具用低温度，写作可调高。

</details>

阅读：《大模型应用》的[训练过程](大模型应用.md#训练过程)。选读：[进阶：训练过程](大模型应用%20-%20进阶.md#训练过程)。

自测：

1. 大模型的训练分为哪几个阶段？（见[三个阶段](大模型应用.md#1-三个阶段)）
2. PPO、DPO 和 GRPO 有什么区别？（见[DPO](大模型应用.md#3-dpo)、[GRPO 与三者的选择](大模型应用.md#4-grpo-与三者的选择)）
3. RLHF 中的奖励模型是怎样训练的？（见[RLHF 与 PPO](大模型应用.md#2-rlhf-与-ppo)）

<details>
<summary>参考要点</summary>

1. 预训练：在海量文本上预测下一个 Token，获得语言能力和知识，但只会续写；监督微调：用指令和人工编写的回答训练，学会按对话格式回答、遵循指令；偏好对齐：用“两个回答哪个更好”的数据让回答更有帮助、更安全，这类目标难写标准答案，但比较容易。
2. PPO 在线生成回答，奖励模型打分、价值模型给出预期，加载 4 个模型、训练 2 个；DPO 不训练奖励模型、不在训练中生成回答，直接用离线偏好对训练，只需策略模型和参考模型，简单稳定；GRPO 去掉价值模型，每题生成一组回答、以组内平均分为预期，适合能用规则判对错的推理训练；PPO 和 GRPO 能探索出训练数据之外的更好回答。
3. 标注员把同一提示词的 4～9 个回答按好坏排序，两两组成偏好对（9 个回答 36 对）；奖励模型输入提示词和回答、输出一个分数，损失为 -log σ(r<sub>w</sub> - r<sub>l</sub>)，使较好回答得分更高，例如分数 1.2 和 0.3 时损失约 0.34。

</details>

动手：用 Python 按[DPO](大模型应用.md#3-dpo)一节的公式，对几组给定的 chosen 和 rejected 对数概率计算 DPO 损失，观察 β 取 0.1 和 0.5 时损失的变化。

预期：两个回答相对参考模型的变化都为 0 时损失为 log 2 ≈ 0.693；较好回答高 2、较差回答低 1 时，β = 0.1 的损失约 0.554，β = 0.5 约 0.201，β 越大，损失对同样的概率差越敏感：较好回答的变化大于较差回答时损失更低，小于时更高，相等时不变。

### 第 5 天：微调与量化

先判断什么时候该微调、什么时候用 RAG 或提示词就够了。LoRA 是最常用的微调方法；量化一节中 GPTQ 与 AWQ 可以略读。

Embedding 把文本变成向量，相似度检索靠它完成。向量索引回答数据量大时为什么要用近似检索，重点是 HNSW，IVF 与 PQ 可以略读。

阅读：《大模型应用》从[Embedding 与相似度](大模型应用.md#embedding-与相似度)读到[向量索引](大模型应用.md#向量索引)。

自测：

1. 文本是怎样变成向量的？为什么用余弦相似度？（见[向量与余弦相似度](大模型应用.md#1-向量与余弦相似度)）
2. HNSW 的原理是什么？（见[HNSW](大模型应用.md#2-hnsw)）
3. 为什么需要近似最近邻检索？（见[为什么需要近似检索](大模型应用.md#1-为什么需要近似检索)）

<details>
<summary>参考要点</summary>

1. 分词后输入 Transformer 编码器，每个 Token 得到一个向量，再池化（取 [CLS] 或平均值，与训练时一致）成固定长度的向量并归一化；对比学习使意思相近的文本向量靠近；余弦相似度看方向是否接近，归一化后等于点积、计算更快，排序与欧氏距离等价。
2. 把向量组织成多层图，每个向量连接附近的若干向量，层越高向量越少、连线跨度越大，最下层包含全部向量；查询从最上层的入口开始，上面各层只保留一个最近节点，贪心地走向查询，走不动就下降一层，最下层保留 efSearch 个候选扩展邻居，从中取前 K 个，思路类似跳跃表；上层的长连线让查询几步就到目标附近，12.4 万个向量上每次只算约 1300 次距离（暴力检索的 1.1%）；过滤掉大部分向量、大量删除和内存放不下时会变差；M、efConstruction、efSearch 在速度、内存和召回率之间权衡。
3. 逐个比较时，100 万个 1024 维向量每次查询约 10 亿次乘加，数据量和并发大时太慢；ANN 索引用少量精度换速度，可能漏掉个别真正最近的向量。

</details>

<summary>参考要点</summary>

</details>

<summary>参考要点</summary>

1. 召回的 K 是每路交给重排的候选数（如 50），在评测集上取召回率不再明显上升的位置，有重排时可以取大些；放进提示词的 K 是重排后保留的数量（如 3～5），太大增加成本、混入无关或旧版本资料，太小答不全，按端到端正确率和上下文预算确定。

3. 原始问题常不适合直接检索：有指代（“那 ConcurrentHashMap 呢”）时结合历史补全；问题太短时用 HyDE 先生成假设的回答再检索；多个子问题拆开分别检索再合并，RAG-Fusion 改写成多个查询后用 RRF 合并；代价是多一次模型调用。

</details>

<summary>参考要点</summary>

</details>

3. 工作流的步骤和顺序由代码事先写好，模型只做其中某些步骤，可预测、成本可控，适合步骤固定的业务；Agent 由模型决定下一步，适合无法事先确定步骤的开放任务，但成本高、错误会累积（每步 95% 时连续 10 步约 60%），所以先尝试单次调用或工作流；判断看步骤和步骤之间的转移规则能否事先写清，写不全才交给 Agent；实际常把两者组合，退款这类固定流程走工作流，商品咨询交给 Agent。

</details>

<details>
<summary>参考要点</summary>

1. ReAct 让推理和行动交替：先思考，再调用工具，把真实结果作为观察放回上下文再思考；与思维链相比，事实来自外部而不是模型的记忆，HotpotQA 的分析中思维链失败案例 56% 是编造事实，ReAct 为 0%；适合下一步取决于上一步结果、步数不多的任务，缺点是只能串行、长任务容易偏离目标。
2. 先规划后执行先一次生成带依赖的步骤列表，按依赖执行、无依赖的步骤并行，失败或结果不符时重规划（次数设上限），进度容易展示和恢复，但计划可能与实际不符；ReAct 每步根据中间结果调整，但每步都要调用一次模型，长任务容易偏离；实际常结合使用，每个步骤内部用 ReAct。

### 第 21 天：稳定性与安全

稳定性一节把超时、重试、限流、降级和熔断用到模型调用上，重点是模型调用与普通接口的不同：生成慢，超时要按输出长度估算，流式输出还可能中途断开。安全一节先解释为什么靠提示词挡不住注入，再讲怎样限制模型被诱导后能造成的后果。

阅读：《大模型应用》从[稳定性](大模型应用.md#稳定性)读到[大模型应用的安全](大模型应用.md#安全)。

自测：

1. 调用模型接口时怎样设置超时和重试？（见[超时](大模型应用.md#1-超时)、[重试与指数退避](大模型应用.md#2-重试与指数退避)）
2. 流式输出中途断开怎么办？（见[流式输出中途断开](大模型应用.md#4-流式输出中途断开)）
3. 怎样防御提示词注入？（见[限制模型能造成的后果](大模型应用.md#2-限制模型能造成的后果)）

<details>
<summary>参考要点</summary>

1. 非流式请求的总超时要大于 TTFT + 最大输出 Token 数 × TPOT，例如 1000 个 Token、30 毫秒时要 30 多秒；流式请求分别设首 Token 超时、间隔超时和总时长上限，心跳不算内容；429、5xx、超时可以重试，400、401 直接失败，按指数退避加随机抖动、遵守 Retry-After，次数设上限且只在一层重试。
2. 还没输出任何内容时直接重试，用户感知不到；已输出部分文字时，把已输出的部分作为 assistant 消息的开头请求续写（如 DeepSeek 的对话前缀续写），不支持就丢弃重新生成并通知前端清空；工具调用的参数只输出了一半时不能执行，丢弃后重新请求。
3. 提示词注入指通过输入的内容改变模型原本的指令，指令也可能藏在网页、文档或工具结果中（间接注入）；指令和资料最终拼成同一个 Token 序列，模型无法可靠区分，提示词只能降低风险，重点是限制后果；外部内容标注为不可信，工具按最小权限提供、在代码中按当前用户校验，高风险操作人工确认；读过不可信内容的任务不给对外发送的工具，前端不自动加载输出中的外部图片，防止数据外泄；输出转义、查询参数化，提示词中不放密钥，记录审计日志。

</details>

动手：参照[重试与指数退避](大模型应用.md#2-重试与指数退避)一节的代码，用 Python 写一个最多尝试 3 次的重试函数，用模拟接口测试：前两次返回 429、第三次返回结果时，打印每次等待的时间；再让模拟接口返回 400，确认没有重试。

预期：两次 429 后分别等待 0.25～0.5 秒和 0.5～1 秒（基准间隔 0.5 秒、1 秒，随机抖动取它的 0.5～1 倍），第 3 次拿到结果；返回 400 时只调用 1 次就抛出异常。

算法（链表，困难）：[25. K 个一组翻转链表](https://leetcode.cn/problems/reverse-nodes-in-k-group/)，题解见[K 个一组翻转链表](Leetcode%20题解%20-%20链表.md#11-k-个一组翻转链表)。

综合题：设计一个企业内部的智能客服：用户的问题怎样分流到知识库问答和工具调用？怎样评测效果？怎样控制延迟和成本？出现提示词注入时怎样限制损失？（见[意图识别与路由](大模型应用.md#意图识别与路由)、[RAG 的评测](大模型应用.md#评测与优化)、[Agent 的评测](大模型应用.md#2-评测)、[延迟与成本](大模型应用.md#延迟与成本)、[安全](大模型应用.md#安全)）

<details>
<summary>答题思路</summary>

1. 分流：意图路由，规则处理“转人工”、带订单号这类精确率高的情况，其余交给分类模型或大模型并限制为枚举值，低置信度时反问或转人工；制度、产品类问题走 RAG，查询和办理走带工具的 Agent，退款这类固定流程写成工作流。
2. 评测：路由用分类评测集和混淆矩阵；RAG 看 Recall@K、MRR 和忠实度、答案相关性，效果差时按解析、切片、检索、重排、生成的顺序排查；Agent 看任务成功率和 pass^k；线上失败的会话加入评测集回归。
3. 延迟：限制输出长度，流式输出缩短用户看到第一个字的时间，互不依赖的工具并行执行；成本：不变的内容放在前面命中前缀缓存，控制工具返回的内容，简单问题交给小模型。
4. 注入：外部资料标注为不可信；用户身份取自登录会话，工具在代码中校验订单属于当前用户并按最小权限提供；退款只生成待确认的申请，由用户确认后走普通业务接口执行；输出转义，记录审计日志。

</details>
